# ХАБАР

Offline-first система полевых донесений.

Боец или оператор в поле создаёт структурированное донесение без всякой связи.
Донесение хранится на устройстве. Как только появляется любой канал, данные сами
уходят в пункт управления в правильном порядке и без дублей.

Полная постановка задачи, границы проекта, план на 10 дней и сценарий демо —
в [`docs/spec.md`](docs/spec.md). Контракт с сервером — в [`docs/api.md`](docs/api.md).
Поминутный сценарий выступления — в [`docs/demo.md`](docs/demo.md).

## Что уже работает в этом скелете

| Модуль | Состояние |
|---|---|
| M1 Создание донесения | форма, справочник типов, фото со сжатием, приоритет |
| M2 Локальное хранилище | Dexie/IndexedDB, фото как Blob, переживает убийство приложения |
| M3 Очередь синхронизации | UUID с клиента, идемпотентность на сервере, приоритеты, backoff, автозапуск, экран очереди |
| M3 Докачка вложений | чанки по 64 КБ, продолжение с места обрыва по `received_bytes` |
| M4 Офлайн-карта | Leaflet, кэш тайлов в service worker, ручная постановка точки, потеря GNSS |
| M5 Панель пункта управления | `dashboard.html`: список, карта, фильтры, время приёма |
| M6 Голосовое донесение | запись с вырезанием тишины, доставка, распознавание на сервере (faster-whisper) |
| M7 Защита данных | база зашифрована AES-GCM, ключ из ПИН-кода; быстрое стирание |

Честно про незакрытое: расшифровка приходит текстом, но по полям донесения не
раскладывается — `extract_fields` в `server/reports/asr.py` пока заготовка.
Оператор пункта управления видит текст рядом с исходным аудио и заполняет поля
сам.

## Шифрование локальной базы

Ключ выводится из ПИН-кода оператора через PBKDF2 (250 000 итераций), живёт
только в памяти вкладки и на диск не попадает ни в каком виде. Закрыли
приложение — ключа нет.

Что зашифровано: тип донесения, описание, координаты, количество, позывной и
байты всех вложений. Что остаётся открытым: `id`, `priority`,
`created_at_device`, `sync_state` — по ним Dexie строит индексы и работает
очередь. На изъятом устройстве видно, что донесений было столько-то, столько-то
из них срочные и созданы тогда-то; не видно ни одного слова текста, ни одного
байта фото.

Два следствия, которые надо понимать и не прятать в питче:

- **Без ПИН-кода синхронизация не идёт.** Отправить донесение можно только
  расшифровав его. Альтернатива — держать ключ рядом с данными, но такое
  «шифрование» не защищает ни от чего.
- **Забытый ПИН-код означает потерю локальных данных.** Восстанавливать нечем,
  и это осознанно: любой механизм восстановления был бы вторым ключом.

Стирание доступно прямо с экрана замка, без ввода кода. В поле важнее суметь
уничтожить данные, чем защитить их от уничтожения.

Смены ПИН-кода нет: она требует перешифровать всю базу. Сейчас код меняется
только через стирание.

## Голосовое донесение

Три части, каждую можно отключить отдельно.

### Вырезание тишины на устройстве

Оператор наговорил сорок секунд, из них речи двенадцать. По узкому каналу мы
гнали бы сорок. Гейт (`client/src/vad.js`) ставит запись на паузу в тишине и
снимает с паузы на речи — перекодирования нет, кодек просто не получает пауз.

Замерено на дорожке 15 с, из которых 6 с тишины: **26,8 КБ против 46,0 КБ**
без гейта. Оператор видит цифру сразу: «срезано 6 с тишины».

Побочный эффект важнее экономии: Whisper галлюцинирует на тишине и шуме, выдавая
обрывки фраз из обучающих данных там, где ничего не говорили. Меньше тишины на
входе — меньше выдуманного текста на выходе.

Основной режим — **Silero VAD v5** через ONNX Runtime. Если среда или модель не
поднялись (первая запись случилась без связи, старый браузер), включается
запасной режим по громкости: грубее, но в шуме ошибается в безопасную сторону —
оставляет лишнее, а не режет речь. Не поднялось вообще ничего — пишем всё
подряд: потерять донесение из-за неудавшегося VAD недопустимо.

Про вес, чтобы не было сюрприза. Модель Silero — 2,3 МБ, лежит в репозитории.
Среда выполнения ONNX — **14 МБ**, в репозитории её нет: `scripts/copy-ort.mjs`
раскладывает её из `node_modules` при `npm install`. Грузится она по требованию,
при первой записи голоса, и дальше живёт в кэше service worker. Холодный старт
приложения от неё не страдает. Если решите, что 14 МБ того не стоят, удаление
`vad.js` и вызова гейта в `media.js` вернёт запись как была — запасной режим по
громкости уже написан и работает без всяких зависимостей.

### Распознавание на сервере

По умолчанию **выключено**: модель весит от полугигабайта и скачивается при
первом запуске, а на демо это не всегда уместно. Включается одной переменной:

```bash
KHABAR_ASR_ENABLED=1 KHABAR_ASR_MODEL=small python manage.py runserver
```

Распознавание уходит в фоновый поток: держать HTTP-соединение с телефоном в поле
на десятки секунд нельзя. Клиент получает ответ сразу, расшифровка появляется на
панели управления позже. Статус виден там же: `pending`, `running`, `done`,
`failed`, `disabled`.

Догнать расшифровки, которых нет (демо прошло с выключенным распознаванием):

```bash
KHABAR_ASR_ENABLED=1 python manage.py transcribe_pending
```

Про качество говорим прямо, а не рекламируем. По-русски Whisper работает хорошо.
По-казахски — слабо: язык низкоресурсный для этой модели. Смешанную казахско-
русскую речь внутри одной фразы не держит ни одна открытая модель. Для казахского
стоит посмотреть модели **ISSAI Назарбаев Университета**, обученные на корпусе
KSC2 (около 335 часов, CC BY 4.0), и подставить их в `KHABAR_ASR_MODEL` вместо
Whisper.

Поэтому на панели управления расшифровка показывается **рядом с исходным аудио**
как черновик для оператора, а не как готовое заполнение полей.

### Язык

Оператор выбирает язык один раз на вкладке «Ещё», и он уезжает вместе с
донесением. Это осознанно вместо автоопределения: на короткой зашумлённой записи
с переходами между языками определитель ошибается чаще, чем человек, который и
так знает, на чём говорит.

## Быстрый старт

### Сервер

```bash
cd server
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
python manage.py migrate
python manage.py runserver 0.0.0.0:8000
```

Без переменных окружения база — SQLite в `server/db.sqlite3`. Для PostgreSQL
задайте `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_HOST`.

### Клиент

```bash
cd client
npm install
npm run dev -- --host
```

Откроется на `http://localhost:5173`. Запросы к `/api` проксируются на
`http://localhost:8000`. Панель пункта управления — `/dashboard.html`.

### Всё сразу

```bash
docker compose up --build
```

Клиент на `http://localhost:5173`, сервер на `http://localhost:8000`.

## Проверка ключевых сценариев

Это то, на чём строится демо. Прогоняйте регулярно.

**Идемпотентность.** Отправьте одно и то же донесение дважды:

```bash
curl -X POST http://localhost:8000/api/v1/sync/reports \
  -H 'Content-Type: application/json' \
  -d @docs/samples/report.json
# первый раз  -> [{"id":"...","result":"accepted"}]
# второй раз  -> [{"id":"...","result":"duplicate"}]
```

`duplicate` для клиента — успех. Запись помечается отправленной.

**Живучесть.** Режим полёта, создать три донесения, убить вкладку, открыть заново.
Все три на месте, состояние «в очереди».

**Докачка.** Начать загрузку фото, оборвать сеть, включить снова. В логах сервера
второй чанк уходит с ненулевым `offset`, файл не грузится заново.

## Структура

```
client/            PWA: Vite + Dexie + Leaflet, без фреймворка
  src/db.js        схемы reports / attachments / outbox, шифрование записей
  src/sync.js      ядро проекта: очередь, приоритеты, backoff, чанки
  src/crypto.js    примитивы AES-GCM и вывод ключа из ПИН-кода
  src/vault.js     ключ в памяти вкладки, проверка ПИН-кода
  src/vad.js       Silero VAD: пауза записи в тишине, запасной режим по громкости
  src/geo.js       GNSS, определение потери сигнала, источник координат
  src/ui/          экраны: форма, список, очередь, карта
  public/sw.js     офлайн-оболочка и кэш тайлов карты
server/            Django + DRF
  reports/models.py    Report, Attachment; PK = UUID клиента
  reports/views.py     три метода контракта + health
  reports/asr.py       распознавание речи, faster-whisper в фоновом потоке
docs/              постановка задачи, контракт, сценарий демо
```

## Границы

Не делаем в этой версии и говорим об этом прямо: Bluetooth mesh и обмен между
устройствами, свой радиопротокол, криптография уровня боевой системы, интеграция
с телеметрией БПЛА, спутниковые каналы, сложное разрешение конфликтов при
параллельной правке. Причина — десять дней. В питче это дорожная карта, а не пробел.

Не режется никогда: локальное хранилище и очередь синхронизации с
идемпотентностью. Без них проекта нет.
